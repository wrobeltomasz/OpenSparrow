OpenSparrow — Admin Panel Overview
==================================
The Admin panel (/admin/) is where the entire OpenSparrow application is configured:
tables, forms, dashboards, calendars, workflows, automations, users, and system maintenance.
Available to the admin role (and partially to editor). All application configuration is stored
in the database (the spw_config table, one JSONB row per key) — no code changes and no config
files to edit; only database.json and security.json remain on disk as bootstrap files.

Current version: 3.1.
Stack: PHP 8.4+, PostgreSQL 14+, vanilla JavaScript (ES6+). No npm, no composer required.
License: LGPL v3. Self-hosted, works fully offline.


SETUP & INSTALLATION
--------------------
1. Open the app — the first-run setup wizard (setup.php) configures the database connection.
   (Alternatively copy config/database.json.example to config/database.json manually.)
2. Open /admin — click System → Database → Initialize System Tables.
3. Log in as admin with the randomly generated password shown once in the setup wizard —
   change it after first login.
Docker: docker compose up -d --build → http://localhost:8080
System tables live in the PostgreSQL schema from database.json (default "app"),
all prefixed spw_.


Navigation sections (collapsible left sidebar): Overview, Data Management, Workflows,
Knowledge Base, System. A Docs button in the header opens built-in searchable documentation
(Getting Started / Schema / Grid Features / Admin Panel / Troubleshooting).


OVERVIEW (landing tab)
----------------------
Dashboard shown on entering the admin panel: application version, database size,
recent record activity, and recent cron runs.


DATA MANAGEMENT
---------------
Schema:
  - Manage tables and columns ("schema" config key)
  - Global settings: default grid page size, visibility options
  - Per table: display name, icon, hidden flag (excludes from menu), default sort,
    initial load limit
  - Per column: name, type (string / int / enum / FK / M2M / file / virtual), display
    name, description (grid header tooltip), nullable, unique, readonly, default value,
    regex validation with custom error message, enum options with colors, FK config
    (referenced table + column + display column)
  - Drag-and-drop column reordering
  - Subtable configuration (FK back-references shown inside edit forms)
  - M2M (many-to-many) configuration
  - Images: per-table switch enabling a record image gallery — display label, max
    images per record (1-50), and whether a thumbnail column appears in the grid.
    Images are stored as regular files (spw_files) linked to the record, so the
    Files module's size and extension limits still apply.
  - Highlight Rules: per-table list of row-highlighting conditions for the grid —
    column, operator (==, !=, >, >=, <, <=, contains), value, and a color; rules are
    evaluated in order and the first match colors the whole row. Same rule shape as
    the Views module's color rules, applied at the table level instead of per column.

Schema — inner tabs (reachable from inside the Schema tab, not as separate sidebar items):
  - Add Table: wizard for creating a new PostgreSQL table and registering it in the schema
  - Menu Preview: drag-and-drop editor of the frontend sidebar navigation ("menu" config key)
    — visibility, order, nesting; saved automatically on drop
  - Schema Map (ERD): read-only entity-relationship diagram of all tables with FK relations
    drawn as arrows; click a table to jump to its editor, with zoom and pan controls
  - M2M Builder: visual builder for many-to-many relations — left/right FK tables,
    junction table name, display columns

Dashboard:
  - Add widgets: stat card (COUNT/SUM/AVG aggregate), bar chart, pie chart, table (recent records list)
  - Per widget: title, source table, aggregate (COUNT/SUM/AVG/MIN/MAX), axis columns,
    group-by, filter conditions, width/height, color palette
  - Drag widgets to reorder in a 3-column grid; live preview while editing (uses
    placeholder sample data, not real query results)
  - "Calculate (real data)" button in the query editor runs the widget's current,
    unsaved table/aggregate/WHERE conditions against the real database and shows the
    actual result, so filters and aggregation can be verified before saving

Calendar:
  - Configure event sources: table + date/timestamp column
  - Event title template (which column becomes the title)
  - Color rules (per enum value or fixed hex), optional icon
  - Advance notification days (notify_before_days) per source

CSV Import:
  - Upload CSV, map columns to table fields, preview, import in batches
  - Import history tracked in spw_imports (one row per import run) with per-row
    detail in spw_import_rows_log

Files:
  - File management settings: allowed types, size limits ("files" config key)

User Records:
  - Configures the "My records" panel every user opens from the avatar menu
    ("user_records" config key)
  - Column Mapping tab: per table, which columns are concatenated into each
    assigned record's label
  - Global Settings tab: how many recently-assigned records are shown per table

Views:
  - Read-only PostgreSQL views exposed as grid pages ("views" config key)
  - Create/edit/delete view definitions: name, description, filters, column order
  - Drill-down by group_by levels (e.g. Year → Month → Invoice)
  - Sync discovers views (and column metadata) in the searched schema(s); a Schemas
    tab selects which PostgreSQL schemas beyond the default app schema are searched

Board (Kanban):
  - Configure one or more boards, each as its own card: a source table, a status column
    (its enum options/colors become the board's lanes), card title column, detail fields
    shown on each card, and its own menu name/icon/visibility ("board" config key, a
    "boards" list — one entry per board)
  - Each board appears as its own item nested under one "Board" entry in the sidebar
    menu, the same way Views and Print templates each get a sidebar item under one
    parent — a board only appears once its table and status column are set

Print Templates:
  - Printable report templates bound to a PostgreSQL view ("print" config key)
  - Block editor: heading, text, and table blocks with {column} variables pulled
    from the bound view; optional report parameters (dropdown filters, e.g. by
    employee) resolved either from the column's distinct values or a lookup view
  - Rendered at print.php with automatic A4 pagination and a dedicated print
    stylesheet; saved/validated via api/print.php


WORKFLOWS
---------
Workflow Manager:
  - Guided multi-step entry flows shown to users (e.g. Company → Contact → Deal)
  - Per workflow: title, description, icon
  - Step builder: add / remove / drag-reorder steps
  - Per step: target table, form fields, multi-record option (e.g. several contacts)
  - Per step: optional PostgreSQL procedure called when the user clicks "Next step".
    Pick schema + procedure from a dropdown listing the database's stored procedures;
    one row is then shown per declared IN parameter, each fed either from a workflow
    field (choose the source step and column — the current step or any earlier one)
    or from a fixed value typed in by hand. The procedure runs before the wizard
    advances and receives only form values, never record ids — nothing is written to
    the database until the final review screen. If the procedure raises an exception,
    its message is shown to the user and the wizard stays on the current step, so a
    procedure can act as a server-side validation gate.

Automations:
  - Event-driven rules executed by the backend on record events
  - Two tabs over the same rule set:
      * Record Automations — rules whose actions stay inside OpenSparrow (update fields,
        send notification, create record, send email)
      * n8n Automations — rules that call an outgoing webhook; a rule is filed here as
        soon as one of its actions is a webhook, so the two tabs never overlap. A new
        rule created here starts with the webhook call already added and needs no action
        type picker
  - Rule list shows name, table, event, status; Edit / History / Delete per rule
  - Triggers: After create (INSERT), After update (PATCH), After delete (DELETE)
  - Conditions: AND/OR groups, nestable; operators equals, not equals, contains,
    not contains, is empty, is not empty, numeric/date comparisons, and change
    detection (changed, not changed, changed from, changed to)
  - Actions:
      1. Update fields on this record — not available on delete events (the row is gone)
      2. Send notification — recipient user ID, title, optional link; one notification
         per (rule, record, user, day), duplicates ignored
      3. Create record in another table — target table + field mapping
      4. Send webhook (HTTP request) — offered in the n8n Automations tab only; see below
      5. Send email — queued to spw_automation_emails, delivered by the notification cron
  - Values support variables {{ record.field_name }}, {{ old_record.field_name }},
    {{ current_user.id }} and {{ today }}
  - Webhook action (the integration path for n8n, Make and custom receivers):
      * Method POST / PUT / PATCH / DELETE, http(s) URL — point it at an n8n Webhook node
      * JSON body: { rule_id, event, table, record_id, triggered_by, data } plus old_data
        on update and delete events. An empty payload mapping sends the whole record
        as "data"; otherwise each mapped JSON key gets a resolved template value
      * Secret — when set, the request carries X-Sparrow-Signature: sha256=<HMAC of the
        raw body>, so the receiver can verify origin. Stored encrypted, never shown back
        in the UI; leave the field blank to keep the saved value, or use "Clear secret"
      * Headers — free-form name/value map for the receiver's own auth (e.g. an n8n
        Header Auth credential). Names stay visible; values are stored encrypted and
        never sent back to the browser — leave one blank to keep the saved value,
        remove the row to delete it, and note that renaming a header clears its value.
        Content-Type, Content-Length, User-Agent, Host and X-Sparrow-Signature are set
        by OpenSparrow and cannot be overridden
      * On failure — optional 1 or 2 retries with backoff, applied only to timeouts and
        5xx/429 responses; a 4xx is never repeated. Sending is synchronous, so retries
        delay the user's save (5 s connect / 10 s response timeout per attempt)
      * Webhook and email skip records owned by another user on owner_restricted tables
  - Run History: last 100 executions per rule — time, table, record ID, event,
    status (ok / error / skipped), error message; stored in spw_automation_runs


KNOWLEDGE BASE
--------------
RAG Documents:
  - Upload .txt documents (drag & drop) with comma-separated tags; convert PDF/Word
    to plain text before uploading
  - File list: name, size, tags, date; delete, retag, search by name or tag
  - Statistics: total files and tokens, per-file token counts, query history
  - Configure Ollama (URL, model) and test retrieval-augmented queries directly
  - Optional Ollama Cloud API key (password field) for the paid Ollama Cloud tier;
    stored encrypted at rest, sent as a Bearer token — the settings screen never
    shows the key back, only whether one is configured, with a button to clear it
  - Retrieval uses PostgreSQL full-text search; tag filtering narrows the search


SYSTEM
------
Audit & Snapshots:
  - Log of all record mutations (INSERT / UPDATE / DELETE): timestamp, user, action,
    table, record ID
  - Filter by table, user, action type; view before/after record snapshots

Backup Tables:
  - Manual backup button (SQL dump), list of backups with timestamps
  - Download backup (.sql file); restore from backup (confirmation required)

Cron Notifications:
  - Manual run (trigger the notification cron immediately)
  - Run history (status, output, duration), statistics (avg duration, success rate)
  - Setup guide for the server system cron (cron/notifications.php, e.g. every 15 min)
  - Log cleanup (delete old cron log entries)
  - Email tab: "From" address for queued automation emails (spw_automation_emails); optional
    SMTP delivery (host, port, encryption, username, password, "Test SMTP Connection" button)
    to send authenticated mail instead of the server's PHP mail(). SMTP password is stored
    encrypted and never shown back in the UI. AUTOMATION_EMAIL_FROM env var, if set, locks
    the From address (admin field becomes read-only).

Database:
  - Initialize System Tables (creates/updates spw_* tables — required on first install).
    Runs every pending database migration, so it also applies the table/column descriptions
    added in 3.1; safe to re-run at any time (all statements are idempotent)
  - PostgreSQL schema browser, table creation wizard, column type documentation

Demo Systems:
  - One-click install of a pre-built demo with its own PostgreSQL schema, sample data,
    dashboard widgets, calendar sources, workflows, and views
  - Demo: CRM (companies, contacts, deals, activities, leads, products,
    quotes, invoices, assets) — installs into its own spw_crm schema
  - The CRM demo also seeds three demo user accounts (demo.anna, demo.marek,
    demo.julia) plus the collaboration data tied to them: multi-message comment
    threads on deals, companies, contacts and leads, private notes with reminders,
    record ownership, file and image attachments, and bell-icon notifications —
    so the comment, notes and notification panels are populated right after install
  - Reset button removes the demo data and its configuration entries

Health Check:
  - Database connection status, table bloat analysis, index advisor,
    slow query log, backup status

ETL:
  - Scheduled or on-demand batch import from one or more external source databases
    (MySQL, MariaDB, PostgreSQL, SQLite) or a CSV file fetched from an FTP/FTPS
    server, into local PostgreSQL target tables (driver-based, extensible to
    Oracle/DB2/SQL Server); independent of the removed MySQL Gateway feature
  - Sources tab: define 2+ named source connections (name, driver, host, port,
    database, user, password), each with its own Test connection. A "CSV file
    (FTP/FTPS)" source instead configures protocol (FTP or FTPS), remote directory,
    CSV file name, column delimiter, whether the first row is a header, and passive
    mode — no true SSH/SFTP support (requires ext-ssh2/phpseclib, not bundled)
  - Jobs: each job picks one of the configured sources. Database-source jobs supply
    a read-only source SELECT/WITH query; CSV/FTP-source jobs import the whole file
    on every run (no query). The target is a schema picked from a dropdown (any
    non-system PostgreSQL schema) followed by a table dropdown populated
    dynamically from that schema's tables (spw_* system tables excluded). All jobs
    share an optional column map (source column → target column) and a load
    mode — full refresh (truncate+insert), append, or upsert (ON CONFLICT)
  - Incremental loading via a {{watermark}} placeholder substituted with the last
    seen value of an incremental column (database sources only)
  - Preview shows sample rows before saving; Test connection verifies reachability
    (for CSV/FTP sources, also confirms the configured file exists)
  - Schedule: manual / daily / weekly / monthly, run by cron/cron_etl.php; run
    history (rows read/written, duration, errors) in spw_etl_log. The frequency
    window is enforced per job (a job runs again only once its own scheduled run
    has succeeded within the window) and only counts scheduled (cron) runs, so a
    manual "Run now" or a flow-triggered run never suppresses a job's next
    scheduled run. "Run now" reports failure when the underlying worker exits with
    an error (the captured output is shown either way)
  - Flows tab: chains existing ETL jobs into an ordered sequence via a tile-based
    builder (start, job, job, ..., end tiles; steps reference job ids from the Jobs
    tab and can be reordered/removed). Runs strictly in order and stops immediately
    at the first failing step. Same manual/daily/weekly/monthly schedule model,
    guarded per flow, run by cron/cron_etl_flow.php; run history (overall status,
    failed step) in spw_etl_flow_run_log plus per-step detail in
    spw_etl_flow_step_log

Anonymization (GDPR):
  - Rules per column: table, a date/timestamp column, an age threshold (anonymize
    records older than N days), the PII column, and a replacement value
  - Preview (dry run) counts affected rows without modifying data
  - Schedule: manual / daily / weekly / monthly via cron/cron_anonymization.php
  - Scan Schema suggests PII columns by matching column names against a keyword
    dictionary; run history in spw_anonymization_log
  - Each history entry can expand into a GDPR/EDPB compliance report (JSON, stored in
    spw_anonymization_report) shown inline, with a Download button saving it as a
    .json file for the data-protection record

Migrations:
  - Database migrations tab: list of system migrations (pending / applied),
    "Apply pending migrations" button. Applied migrations are recorded in spw_migrations.
    Two migrations exist:
      3.0_baseline        — the whole spw_* schema (tables, constraints, indexes). The
                            pre-3.0 incremental history was collapsed into this single
                            append-only entry; 3.0 is the first shipped version
      3.1_table_comments  — COMMENT ON TABLE / COMMENT ON COLUMN descriptions for every
                            spw_* table and column. Metadata only: no columns, constraints
                            or indexes change, so the 3.1 table layout is identical to 3.0.
                            After applying it, the descriptions are visible in psql \d+,
                            DBeaver, pgAdmin and anything else reading obj_description()
  - A fresh install via the setup wizard applies both automatically, so new databases
    are created with the descriptions already in place
  - Release migrations tab: config cleanup driven by config/migrations.json —
    tracks files and config keys removed between versions, applied manually on upgrade

Performance:
  - 6 diagnostic sections, each with a Scan button: index advisor (missing indexes with
    recommended SQL), unused indexes, slow query log, table bloat, DB health (connection
    pool, cache hit rate), schema warnings (e.g. table without primary key)
  - Copy SQL buttons for recommended fix queries

Settings:
  - Application settings: system name, theme, menu configuration, notification settings
  - Custom Logo: replace the default frontend header logo (PNG/JPEG/WEBP, up to 2 MB);
    independent show/hide toggle
  - Security configuration stored in config/security.json: CORS, HSTS, CSP modes,
    optional IP whitelist, session timeout, password policy

Users:
  - Three inner tabs: Manage Users, Statistics, Global Settings
  - Manage Users: user list (ID, name, status active/inactive, role); role dropdown
    per user (admin / editor / viewer); activate / deactivate accounts; per-user
    password change dialog with strength meter; add new user form (name + password + role,
    preselected with the configured default role)
  - Statistics: total / active / inactive user counts, breakdown by role, and the
    last 10 user-related audit log entries (who did what, when)
  - Global Settings: org-wide user policy — minimum password length and default role
    for new users, enforced when adding users or changing passwords


SYSTEM TABLES (spw_*)
---------------------
27 system tables, all prefixed spw_ and created in the schema from database.json
(default "app"). Since 3.1 every table and column also carries its description as a
PostgreSQL COMMENT. The full column-by-column reference is docs/DATABASE.md; the DDL
lives in includes/system_tables.php (system_tables_ddl + system_tables_comments_ddl).

Users, authentication and audit:
  spw_users                  — application accounts (username, Argon2id password hash,
                               role, active flag, avatar)
  spw_users_log              — audit trail of every record mutation (who, what action,
                               which table and record, when)
  spw_login_attempts         — login attempt journal for the rate limiter; stores a
                               salted hash of the IP, never the raw address
  spw_record_snapshots       — full before/after row snapshots (JSONB) attached to an
                               audit entry; retention configurable in Settings
  spw_record_owners          — record ownership history; the row flagged is_current
                               drives per-user row filtering

Configuration:
  spw_config                 — DB-backed application configuration, one JSONB row per
                               key, with an optimistic-locking version column
  spw_config_log             — change history of the configuration store (old/new value)
  spw_release_migrations     — applied release migrations (file/config cleanups from
                               config/migrations.json)
  spw_migrations             — applied database migrations (3.0_baseline,
                               3.1_table_comments)

Content attached to records:
  spw_files                  — uploaded files and attachments, including the record
                               image galleries (rows tagged related_field = __image);
                               soft-deleted, served only through the file proxies
  spw_comments               — per-record discussion threads (max 4000 characters)
  spw_notes                  — private per-user notepad, optionally linked to a record
                               and optionally carrying a reminder date+time

Notifications and automations:
  spw_users_notifications    — per-user notification inbox; a uniqueness rule on
                               (user, source record, date) keeps the cron idempotent
  spw_users_notifications_log
                             — run history of the notification cron worker
  spw_automation_runs        — execution log of automation rules (one row per firing)
  spw_automation_emails      — outbound email queue (status, attempts, delivery time)

CSV import:
  spw_imports                — one row per import run (row counts, column mapping,
                               conflict column, status)
  spw_import_rows_log        — per-row rejection detail for skipped rows

Knowledge base (RAG):
  spw_rag_files              — knowledge-base documents, full-text indexed
  spw_rag_chunks             — documents split into retrieval chunks
  spw_rag_queries            — question log and usage metering (tokens, duration, model)
  spw_rag_query_sources      — citations returned for a query, in relevance order

Anonymization (GDPR):
  spw_anonymization_log      — anonymization run history (rules processed, rows scrubbed)
  spw_anonymization_report   — detailed per-run compliance report (JSONB, downloadable)

ETL:
  spw_etl_log                — single-job run history (rows read/written, errors)
  spw_etl_flow_run_log       — flow run history, including the failing step index
  spw_etl_flow_step_log      — per-step detail of a flow run


CONFIGURATION STORE (spw_config table)
--------------------------------------
Application configuration lives in the spw_config table (one JSONB row per key,
optimistic locking via a version column, full change history in spw_config_log).
Read and written through includes/config_store.php — never as files.

  schema        — table/column definitions
  menu          — sidebar navigation structure
  settings      — app name, locale, feature toggles, automation email From address + SMTP
                  delivery settings (host/port/encryption/username, encrypted password)
  dashboard     — widget layout
  calendar      — calendar event sources
  board         — Kanban board (table, status column, card columns)
  workflows     — workflow step definitions
  automations   — automation rules (triggers, conditions, actions)
  views         — view definitions
  files         — file upload settings (allowed types, size limits)
  print         — printout templates
  anonymization — GDPR anonymization rules and dictionary
  user_records  — per-table owner column mapping and record limits
  user_policy   — minimum password length and default role for new users
  rag           — Ollama URL, model, max context files, file size limit, timeout,
                  encrypted Ollama Cloud API key (ollama_api_key_enc)
  etl           — external source connection and import job definitions
  etl_flows     — ordered chains ("flows") of existing ETL job ids, run
                  sequentially, stopping on the first step failure

CONFIGURATION FILES (config/*.json)
------------------------------------
Only bootstrap and distribution files remain on disk:

  database.json       — DB connection (host, port, dbname, user, password, schema);
                        read before any database connection exists, so it cannot live in the DB
  security.json       — CORS, HSTS, CSP, IP whitelist, session and password policy
  migrations.json     — release manifest (files/config keys removed per version)
  demo_meta.json      — installed demo metadata
